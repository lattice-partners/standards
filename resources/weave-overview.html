How Weave works

Weave is a Cursor plugin made of Markdown files: skills, slash commands, and a template. Once installed, Cursor loads it into every agent chat. Each project adds one file, weave.md, that records how that specific repository is built, tested, and verified, and what agents must not do without approval.

Principle skill (always loaded) Task skill (used when the work matches) Slash command (run by a person) Project file Human approval required

Overview

The plugin source lives in this repository. Cursor installs it once per machine or team. Every project that uses it gets its own weave.md. Agents read both on every task.

What is in the plugin

Four kinds of files. Principles are loaded in every chat. Task skills are used when the request matches their description. Commands only run when a person types them. The template defines the shape of weave.md.

Principle skills

8, always loaded
principle-weaveRead weave.md before planning. Follow its components, boundaries, risk rules, and definition of done. Never edit it directly.
principle-securityServer-side auth, no RLS bypasses, no secrets in NEXT_PUBLIC_, no destructive SQL without approval. Private site unless clearly public.
principle-testingTests ship with features. Never delete a failing test to pass. Never call work done if tests did not run.
principle-code-qualitySimple, typed, no dead code, errors handled, Conventional Commits, no em dashes or emojis.
principle-frontend-uxShow-then-edit, read-only tables, wizard modal layout, loading/empty/error states, short copy.
principle-performanceMeasure first, server rendering, no N+1 queries, index filter and RLS columns.
principle-suggested-stackDefault to Supabase, Clerk, Vercel, Railway, and Lattice Design unless the project already chose otherwise.
principle-demoOnly when a demo or mock-up is requested: no database, sessionStorage store, several scenarios.

Task skills

3, used when relevant
lattice-stackHow to set up Supabase, Clerk, and Vercel: branches, RLS with Clerk claims, env vars per environment.
lattice-designVisual system on Tailwind v4: tokens, shell, typography, buttons, modals, menus, motion.
utility-ui-options-toggleBuild three distinct variants of a screen so the team can compare and pick one.

Slash commands

3, run by a person
/setup-weaveInterview the human and inspect the repo, then write weave.md and the AGENTS.md block.
/review-weaveRead-only audit of the repo against the principles and weave.md. Approve or request changes.
/utility-weave-improvementsRead the last 14 days of chats and print a report for the Weave team. Edits nothing.

Template

The first four are filled in per project. The last three are copied unchanged into every project.

Lattice rules vs project rules

An agent works from two sources at once. The plugin holds rules that are the same for every Lattice project. weave.md holds facts that are only true for one repository.

Weave pluginProject weave.md
ScopeEvery repo on every machine where it is installedOne repository
ContainsPrinciples, task skills, commands, templateComponents, verified commands, evidence, boundaries, notes, risk, definition of done
Who changes itWeave team, through a PR to lattice-standardsOnly /setup-weave, after a person approves the diff
Feature agents mayFollow itFollow it and propose corrections, but not edit it
If missingNo Weave behavior at allAgent says so, applies Lattice defaults, and does not invent repo commands or permissions

Setup: /setup-weave

Run once on an existing repository (new or empty repos are not supported yet). The agent inspects the repo, asks one question at a time, and writes nothing until the final approval. Red steps wait for a person.

0

Preflight

Read any existing weave.md and AGENTS.md. Inspect manifests, apps, CI, tests, and docs. Stop if the repo is empty. Never copy secret values.

1

Discover components confirm

Propose each app, service, or shared library with its path, type, runtime, and how it relates to the others. The person confirms or corrects the list.

2

Shared prerequisites

Package manager, runtimes, services and startup order, env var names, test accounts, seed data. Each finding is tagged as confirmed by a file, by a command, by the human, or unresolved.

3

Inspect each component ask before running

Find install, start, test environment, and verification methods. A method counts as verified only if it runs and produces its expected visible result. Missing methods are recorded as gaps.

4

Boundaries and notes confirm

Propose rules for production data, migrations, deploys and merges, and auth changes. Then ask: "What do agents repeatedly misunderstand about this repository?"

5

Draft files

Fill the template to produce weave.md, the AGENTS.md block, a provenance summary, and a list of gaps.

6

Final approval approve

Show full drafts and diffs. Write only after an explicit yes. On reruns, show every addition, change, and removal.

7

Verify and summarize

Read the files back, check they match what was approved, and print a Result block.

A task, start to finish

A walkthrough of one sample prompt in a repo that already has weave.md. The steps come from the Task protocol, Risk, and Definition of done sections of the template.

Sample prompt
Save notes on each client in Supabase so people in an org only see their own org's notes. Add a Notes panel to the client detail page.
1

Read the contract

principle-weave makes the agent read weave.md: the apps/web commands, the "never run migrations against production" boundary, and the note about the shared owner column.

2

Confirm acceptance criteria

Written as things that can be observed, without narrowing the request:

- A signed-in user sees notes for clients in their active org only.
- A user in another org gets zero rows for the same client id.
- Notes panel shows loading, empty, and error states.
- Add, edit, and delete a note from the detail page.
3

Classify risk High: wait for approval

New RLS policies change who can access what, so the task is High. A person must approve both the implementation plan and the verification plan before any code is written.

4

Plan verification

List ways the change could look correct while being wrong (for example, RLS passes locally because the query used the secret key). Derive checks from affected surfaces, invalid input, failure cases, and policy bypasses. Use only methods that weave.md marks as verified.

5

Build, with the matching skills

principle-suggested-stack lattice-stack principle-security principle-performance principle-frontend-ux lattice-design principle-testing principle-code-quality
  • Forward-only migration with RLS in the same file, policy on auth.jwt()->'o'->>'id', text owner column, index on it.
  • Server client forwards the Clerk token. No secret key on user requests.
  • Notes panel is read-only until Edit, with loading, empty, and error states, styled with Lattice tokens.
  • Unit tests plus an RLS test for the cross-org case. Regenerated types committed.
6

Verify and record evidence

Every check is recorded in the same format, against the final commit:

Check:    Cross-org user cannot read notes
Expected: 0 rows for client c_123 as org_B user
Observed: 0 rows
Method:   unit-tests (npm test, rls.spec.ts)
Evidence: test output at commit 4f2a1c9
Status:   verified
7

Definition of done

Complete only if every criterion has direct evidence and every planned check ran without being weakened. If the billing e2e gap blocked a needed check, the status is blocked, not complete.

Which skills each prompt uses

All principle skills are loaded in every chat. A filled dot means the skill shapes the work for that prompt. A ring means the skill is loaded and checked but does not change much. Empty means not used.

Sample prompt Risk weave security testing code-quality frontend-ux performance suggested-stack demo lattice-stack lattice-design ui-options
"Add a Clients page with a searchable table and an Edit modal." Low
"Save client notes in Supabase so each org only sees its own." High
"Make a clickable demo of the onboarding flow for Friday's pitch." Low
"Show me three layout options for the invoice screen." Low
"Move the API to Railway with staging and production deploys." Medium

Risk levels are examples. The agent classifies each real task with the rules in the next section and escalates one level when unsure. If the project chose other tools (for example PlanetScale instead of Supabase), suggested-stack and lattice-stack do not push Lattice defaults.

Risk levels

Copied unchanged into every weave.md. When more than one level applies, the highest wins.

Low

Isolated, reversible, follows an established verification pattern, and does not touch protected behavior.

Agent approves its own plans.

Medium

May affect unrelated behavior, is hard to reverse, or has no established way to verify it.

Human approves the verification plan.

High

Changes who can access what, handles secrets differently, touches production data, moves money, sends external messages automatically, or cannot be rolled back.

Human approves implementation and verification plans.

Review: /review-weave

A manual, read-only audit. Run it on a branch before merging, or on a repo to see how far it is from the standard. It reports and does not fix unless asked.

1

Read weave.md

If it is missing, review against full Lattice defaults and say so in the report.

2

Check the principles

testing security frontend-ux code-quality performance demo

demo is only checked when the change is a mock-up.

3

Skip what the project did not choose

No failures for missing Supabase or Lattice Design when the project uses something else.

4

Grade findings

Each finding cites a path or principle and is tagged blocker should-fix or nit.

5

Verdict

Approve or request changes.

Sample prompt
/review-weave on this branch before I open the PR.

Sample report

Findings
- blocker   supabase/migrations/0012_notes.sql
            Policy uses `using (true)`. principle-security.
- should-fix apps/web/app/clients/[id]/notes.tsx
            No error state for failed fetch. principle-frontend-ux.
- nit       apps/web/lib/notes.ts
            `getData` should say what it returns. principle-code-quality.

- Status: request-changes

Improving the standard

How problems seen in real chats become changes that every project receives.

1 /utility-weave-improvements

Reads the last 14 days of chat transcripts on this machine. Read-only.

2

Report

Findings sorted into security, frustration, configuration, inconsistency, and recommendation, each rated strong or medium.

3

Edit the plugin

Weave team edits the skill, command, or template in plugins/weave/.

4

Version

Bump VERSION and plugin.json, add a CHANGELOG.md entry.

5

Check

npm test validates manifests, versions, frontmatter, and sections. npm run lint:md checks Markdown. CI runs both.

6

Ship

Merge to main. Team marketplace refreshes, or local users restart Cursor.

Quick rules

Only /setup-weave writes weave.md. Feature agents propose corrections. A person approves the diff.
Verified means it ran. A command counts only when it exits successfully and shows its expected result. A zero exit code alone is not enough.
Gaps block completion. Work that depends on a missing verification method is reported as blocked, never complete.
Notes cannot loosen rules. Notes add context. They never weaken a boundary or verification requirement.
No weave.md, no invented rules. The agent applies Lattice defaults and says the file is missing.
Install one copy. If both the marketplace and local copies are installed, the marketplace copy is used and local edits are ignored.
